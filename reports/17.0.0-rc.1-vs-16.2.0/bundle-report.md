# Bundle-size report: `@stellar/stellar-sdk` 17.0.0-rc.1 vs 16.2.0

Generated by `npm run benchmark` on 2026-08-07 (Node v24.13.0, esbuild 0.25.12). baseline = `@stellar/stellar-sdk@16.2.0`, candidate = `@stellar/stellar-sdk@17.0.0-rc.1`. Sizes are of a production esbuild bundle (minified, ESM, `platform: browser`). gzip is the number users download; it is the one to quote.

The baseline ships no prebuilt `browser` root, so both versions resolve ESM source in every scenario. These deltas are a like-for-like code-size comparison; the control below is a secondary check under `platform: node`.

## Build-input fairness (control: bundle from source)

Both versions already resolve source by default, so this control mainly re-checks the headline numbers under different build settings rather than correcting for a UMD baseline. These control builds use `platform: node` (node built-ins external), so they are NOT directly comparable to the `platform: browser` rows above — compare baseline-source to candidate-source *within* this table.

**Summary:** bundled from source (baseline ESM vs candidate ESM), the candidate is **57% larger** for the full SDK and **32% larger** for a classic Horizon import. Subpath imports (`/rpc`, `/contract`) show 38–38% larger. Both versions resolve source in the default numbers too, so the headline table and this control point the same direction.

## Caveats

- Each version is resolved the way a real bundler would resolve it (default export conditions). Neither version ships a prebuilt `browser` root, so both resolve source in every scenario and the watch column is meaningful for both.
- `platform: browser`. A scenario that fails to bundle shows a failure row in the size table above, and is itself a finding (it needs polyfills in the browser).
