# Bundle-size report: `@stellar/stellar-sdk` 16.0.0-rc.1 vs 15.1.0

Generated by `npm run benchmark` on 2026-06-09 (Node v24.13.0, esbuild 0.25.12). baseline = `@stellar/stellar-sdk@15.1.0`, candidate = `@stellar/stellar-sdk@16.0.0-rc.1`. Sizes are of a production esbuild bundle (minified, ESM, `platform: browser`). gzip is the number users download; it is the one to quote.

Negative Δ means the candidate is smaller. **These are default-resolution numbers:** a bundler resolves the baseline's root import to its prebuilt `browser` UMD bundle (which cannot be tree-shaken) and the candidate to ESM source, so the `full` / `horizon-classic` deltas mix a real code-size win with that build-input difference. The `/rpc` and `/contract` rows have the baseline also resolve source (CJS vs ESM). The control below isolates the real difference.

## Build-input fairness (control: bundle from source)

The baseline has no root ESM build, so its default root import resolves a prebuilt `browser` UMD bundle that can't be tree-shaken. Re-bundling each version from its **source** entry (baseline via CJS `main`, candidate via ESM `module`) isolates the real code-size difference. These control builds use `platform: node` (node built-ins external), so they are NOT directly comparable to the `platform: browser` rows above — compare baseline-source to candidate-source *within* this table.

| Scenario | baseline default (UMD) | baseline source (CJS) | candidate source (ESM) | candidate vs baseline source |
| --- | --- | --- | --- | --- |
| full | 273.5 KB | 229.9 KB | 104.3 KB | 55% |
| horizon-classic | 273.6 KB | 230.0 KB | 74.5 KB | 68% |

**Summary:** bundled from source (baseline CJS vs candidate ESM), the candidate is **55% smaller** for the full SDK and **68% smaller** for a classic Horizon import. Subpath imports (`/rpc`, `/contract`) show 50–51% smaller. The larger ~70% for default root imports also reflects the baseline shipping a non-tree-shakeable UMD bundle, not only less code in the candidate.

## Caveats

- Each version is resolved the way a real bundler would resolve it (default export conditions). The candidate resolves ESM source; the baseline's **root** import resolves its `browser` field, a prebuilt UMD bundle — which is why the baseline `full` and `horizon-classic` are an identical size (no tree-shaking) and the baseline watch row shows nothing (esbuild can't see module names inside the prebuilt bundle). Baseline subpaths (`/rpc`, `/contract`) have no `browser` field and do resolve source. This is the honest user-facing number, not a forced same-entry comparison — but treat the baseline watch column as unreliable.
- `platform: browser`. A scenario that fails to bundle shows a failure row in the size table above, and is itself a finding (it needs polyfills in the browser).
