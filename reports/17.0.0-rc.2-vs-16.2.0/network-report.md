# Network transport report: `@stellar/stellar-sdk` 17.0.0-rc.2 vs 16.2.0

Generated by `npm run net` on 2026-08-18 (Node v24.13.0). The same `Horizon.Server.loadAccount()` call runs against a local loopback server that returns a fixed account payload instantly. This isolates the SDK's request-build, HTTP-client, and JSON-parse overhead from real network latency. Each config runs in its own process.

## Summary

the candidate (fetch) is about the same as the baseline (fetch); within the candidate, fetch vs the axios opt-in is 26% faster on loopback throughput. Both baseline and candidate default to native `fetch`, so the baseline-vs-candidate difference is SDK request/parse overhead, not a transport change; only the axios opt-in row is a transport comparison. Real-world calls are dominated by network latency, so none of this usually decides request speed in production.

## Caveats

- **Loopback, not the internet.** Wire latency, TLS, DNS, and distance are removed on purpose. Real-world `loadAccount` time is dominated by those, not by the client library — so this measures client overhead only, and in production the choice of fetch vs axios is usually not what determines request speed.
- Connection reuse (keep-alive) differs between clients and is part of what this captures; it matters more under sustained load than for a single call.
- Single machine, single run; treat differences under ±5% as a wash.
