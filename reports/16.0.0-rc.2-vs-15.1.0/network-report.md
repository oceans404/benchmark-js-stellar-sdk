# Network transport report: `@stellar/stellar-sdk` 16.0.0-rc.2 vs 15.1.0

Generated by `npm run net` on 2026-06-11 (Node v24.13.0). The same `Horizon.Server.loadAccount()` call runs against a local loopback server that returns a fixed account payload instantly. This isolates the SDK's request-build, HTTP-client, and JSON-parse overhead from real network latency. Each config runs in its own process.

## Summary

the candidate (fetch) is 20% faster than the baseline (axios); within the candidate, fetch vs the axios opt-in is 18% faster on loopback throughput. This gap is **likely connection-reuse behavior** (native fetch/undici pools keep-alive connections by default; the axios client may not) rather than per-operation CPU cost — though this benchmark does not toggle keep-alive to isolate it. And real-world calls are dominated by network latency, so this rarely decides request speed in production.

## Caveats

- **Loopback, not the internet.** Wire latency, TLS, DNS, and distance are removed on purpose. Real-world `loadAccount` time is dominated by those, not by the client library — so this measures client overhead only, and in production the choice of fetch vs axios is usually not what determines request speed.
- Connection reuse (keep-alive) differs between clients and is part of what this captures; it matters more under sustained load than for a single call.
- Single machine, single run; treat differences under ±5% as a wash.
