# Bundle-size report: `@stellar/stellar-sdk` v16-rc vs v15

Generated by `npm run benchmark` on 2026-06-09 (Node v24.13.0, esbuild 0.25.12). Sizes are of a production esbuild bundle (minified, ESM, `platform: browser`). gzip is the number users download; it is the one to quote.

## Size by scenario

| Scenario | v15 gzip | v16 gzip | Δ gzip | v16 brotli | v16 raw |
| --- | --- | --- | --- | --- | --- |
| Full SDK (`import * as`) | 273.5 KB | 112.0 KB | -59.0% | 95.2 KB | 418.2 KB |
| RPC only (`/rpc`) | 155.2 KB | 76.3 KB | -50.8% | 65.3 KB | 295.7 KB |
| Classic Horizon app | 273.6 KB | 82.3 KB | -69.9% | 70.2 KB | 316.5 KB |
| Contract client (`/contract`) | 173.2 KB | 86.2 KB | -50.2% | 73.6 KB | 333.9 KB |

Negative Δ means v16 is smaller. **These are default-resolution numbers:** a bundler resolves v15's root import to its prebuilt `browser` UMD bundle (which cannot be tree-shaken) and v16 to ESM source, so the `full` / `horizon-classic` deltas mix a real code-size win with that build-input difference. The `/rpc` and `/contract` rows have v15 also resolve source (v15 CJS, v16 ESM). The control below isolates the real difference.

## Build-input fairness (control: bundle from source)

v15 has no root ESM build, so its default root import resolves a prebuilt `browser` UMD bundle that can't be tree-shaken. Re-bundling each version from its **source** entry (v15 CJS via `main`, v16 ESM via `module`) isolates the real code-size difference. These control builds use `platform: node` (node built-ins external), so they are NOT directly comparable to the `platform: browser` rows above — compare v15-source to v16-source *within* this table.

| Scenario | v15 default (UMD) | v15 source (CJS) | v16 source (ESM) | v16 vs v15 source |
| --- | --- | --- | --- | --- |
| full | 273.5 KB | 229.9 KB | 104.3 KB | 55% |
| horizon-classic | 273.6 KB | 230.0 KB | 74.5 KB | 68% |

**Summary:** bundled from source (v15 CJS vs v16 ESM), v16 is **55% smaller** for the full SDK and **68% smaller** for a classic Horizon import. Subpath imports (`/rpc`, `/contract`) show 50–51% smaller. The larger ~70% for default root imports also reflects v15 shipping a non-tree-shakeable UMD bundle, not only less code in v16.

## Caveats

- Each version is resolved the way a real bundler would resolve it (default export conditions). v16 resolves ESM source; v15's **root** import resolves its `browser` field, a prebuilt UMD bundle — which is why v15 `full` and `horizon-classic` are an identical ~273 KB (no tree-shaking) and the v15 watch row shows nothing (esbuild can't see module names inside the prebuilt bundle). v15 subpaths (`/rpc`, `/contract`) have no `browser` field and do resolve source. This is the honest user-facing number, not a forced same-entry comparison — but treat the v15 watch column as unreliable.
- `platform: browser`. A scenario that fails to bundle shows a failure row in the size table above, and is itself a finding (it needs polyfills in the browser).
